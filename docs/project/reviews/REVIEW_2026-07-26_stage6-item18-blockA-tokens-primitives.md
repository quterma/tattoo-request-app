## Review 1

### Findings

1. **should-fix — The new fluid heading clamps prevent a full 200% text resize at wide
   viewports.** `src/shared/styles/tokens.css:32-33` caps h1 at `2.25rem` over a `1.75rem`
   minimum, and h2 at `1.5rem` over a `1.25rem` minimum. At a 1280 CSS-pixel viewport, 200%
   browser zoom reduces the layout viewport to roughly 640 CSS pixels; the formulas therefore
   compute about 33.44px for h1 and 22.88px for h2 instead of twice their unzoomed 36px/24px
   sizes. CSS pixels themselves enlarge under zoom, but the viewport-dependent term shrinks, so
   the net visual increase is only about 186% / 191%. MDN's `clamp()` accessibility guidance says
   that, when `clamp()` controls text size, the maximum relative value should be at least twice
   the minimum so text can scale to 200%. This is an external-boundary problem that the four
   fixed-width screenshots and component tests cannot see. Please either revise the formulas so
   zoom does not suppress 200% resizing (for example, a calculation whose viewport contribution
   does not defeat the relative contribution), or provide measured browser evidence that the
   shipped formulas still satisfy the project's applicable resize-text requirement. The same
   issue exists in the supplier-only display clamp at `src/shared/styles/tokens.css:43`; it should
   be corrected before Block B consumes it.

### Focus-question results

- **Border mechanism:** confirmed. In the baseline, the later plain `:root`
  `--color-border: #e0e0e0` won the custom-property cascade, but rendered Tailwind borders read
  `--border` directly. No execution-affecting code reads `var(--color-border)`, so deleting the
  token does not change a rendered border.
- **Spacing:** confirmed for the current tree. All 18 JSX `Stack` call sites pass an explicit gap;
  the `Section` and `Page` defaults reproduce the former defaults; and existing `className`
  overrides remain last in `cn()`. Block A therefore moves no spacing. Deferring flow-margin
  removal is the correct checkpoint boundary because removing it without the Block B call-site
  edits would create a knowingly broken intermediate tree.
- **Heading curve and 1024px cap:** the visual endpoints are defensible as a consistency choice,
  and capping at 1024 rather than 1280 is not itself a viewport-support issue. The zoom interaction
  in Finding 1 is the issue.
- **Stack default:** acceptable for this block. `gap-4` has zero JSX call sites and every current
  call site is explicit. The narrower union is a deliberate API change, not a rendered regression.
- **External feasibility:** Tailwind's current official documentation explicitly supports
  `@theme inline` and the `h-(--custom-property)` form; the repository pins Tailwind v4 and its
  successful type/build pipeline exercises generation. MDN classifies `clamp()` as widely
  available since July 2020. No version- or browser-fragile syntax was found beyond the
  accessibility behavior in Finding 1.
- **Scope:** no change in this diff introduces a new visual identity. Token convergence, named
  density variants, and a responsive type scale remain within the task's consistency scope.

## Response 1

### Finding 1 — fluid clamps suppress 200% zoom — **ACCEPTED, fixed**

Reproduced independently before acting. My measurement differs slightly from the review's in the
intermediate number (h1 computes 32.80px at a 640px layout viewport, not 33.44px) but confirms the
finding and its direction:

| | unzoomed @1280 | @200% zoom | effective enlargement |
| --- | --- | --- | --- |
| h1 | 36.00px | 65.60px | **182.2%** |
| h2 | 24.00px | 44.80px | **186.7%** |
| display | 48.00px | 91.20px | **190.0%** |

The mechanism is as described: zoom halves the layout viewport in CSS pixels, so the `vw` term
shrinks exactly when the user asks for larger text. The baseline tree did not have this problem —
flat `2rem` scales to exactly 200% — so the first draft of this scale introduced it.

**Satisfying the `max >= 2 * min` guidance inside `clamp()` is not available here**: with a
1.75rem minimum it demands a 3.5rem (56px) h1 on every page, which is a redesign and out of scope
per the task file's Out of Scope section.

**Fix taken: a breakpoint step instead of a fluid curve** — `--font-size-h1/h2/display` are now
plain rem values with a `@media (min-width: 40rem)` override in `tokens.css`. With no viewport term
at all, every heading scales to exactly **200.0%** under zoom.

This is better than the fluid version on the task's own terms, not merely compliant:

- Identical to the clamp at 320/375 (28/20px) and at 768/1024/1280 (36/24px) — the four widths
  `pnpm shot` captures. The only difference is 640–1024px, where the step renders *larger*
  (36 vs 32.80–34.72px).
- **`.text-display` now reproduces the hero's outgoing `text-4xl sm:text-5xl` exactly at every
  width** — 36px below the breakpoint, 48px at and above. The "up to 2.4px short between
  640–768px" caveat I had recorded for Block B is gone.
- Written as `40rem`, not `640px`, matching the units Tailwind v4 itself emits (verified in the
  compiled bundle: `@media (min-width:40rem)`). A rem breakpoint moves with the user's base font
  size, so a larger default gets the larger headings at the point the text needs them.

Verified after the fix: `pnpm qg` PASS (33 files / 408 tests, 0 lint errors); compiled bundle now
contains **zero** `clamp(` occurrences and the `@media (min-width:40rem){:root{...}}` step;
`pnpm shot` re-run — 24 captures, `scrollWidth === viewport` on all 24, and 768px inspected
visually (the width whose values moved most).

Scope note: this changes CO-3 row 2–4 values. The task file's CO-3 table and the code comment were
updated to the step's measured numbers (`<640px`: h1 28px, h2 20px · `>=640px`: h1 36px, h2 24px).
No other rendered value moved.
