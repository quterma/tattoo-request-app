## Review 1

### Findings

1. **[should-fix] The selected keyless iframe URL works today but is not a currently documented,
   supported Google Maps embed contract.** At
   `app/[locale]/(public)/location/page.tsx:42`, the implementation correctly follows the
   owner-decided task and the owner's live-browser check proves present-day behavior. However,
   Google's current Maps Embed API documentation specifies
   `https://www.google.com/maps/embed/v1/<mode>?key=...` and explicitly requires an API key; its
   separately documented keyless Maps URLs are navigation/launch URLs, not iframe embeds. Neither
   official surface documents `https://maps.google.com/maps?q=...&output=embed`. Therefore the
   live check cannot establish deprecation policy or production reliability for this legacy
   endpoint. This is not an implementation/spec mismatch—the task deliberately fixed the keyless
   endpoint—but the external-boundary risk must be resolved explicitly before consensus: either
   amend the owner decision to use the supported Embed API, or record acceptance of the
   undocumented-endpoint risk (the three provider links remain a usable fallback if the iframe
   later fails). Sources checked 2026-07-19:
   [Maps Embed API](https://developers.google.com/maps/documentation/embed/embedding-map) and
   [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started).

2. **[should-fix] The reviewed working tree includes an out-of-scope generated-file change.**
   `docs/files-structure.md:160-162` is modified even though the task's Allowed Write Surface
   (`docs/project/tasks/STAGE_6_TASK_07_location_map_embed.md:17-20`) explicitly says generated
   files may not be touched. Its diff also lists Items 11 and 12, which are unrelated to the map
   embed. This contradicts the Handoff's “No other files changed” statement. Exclude/revert
   `docs/files-structure.md` from this block before commit; the review thread itself is the
   expected protocol write.

### Focus-question answers

1. Reusing `addressQuery` is correct. `encodeURIComponent` produces a valid URL-escaped address
   (including `%2C` for commas), and there is no double encoding in the template literal. The
   endpoint support issue is Finding 1, not an encoding defect.
2. Keep `loading="lazy"`. It is required by the task, is browser-native, and lets the browser
   load the iframe when it is near the viewport; Google's supported Embed API example uses the
   same attribute. The map's exact fold position varies by viewport, so forcing eager loading
   would spend third-party bandwidth without a demonstrated UX need.
3. No additional landmark is required for this change. The localized, descriptive `title`
   supplies the frame's accessible name, matching W3C technique
   [H64](https://www.w3.org/WAI/WCAG22/Techniques/html/H64); the visible address and three
   provider links immediately before the iframe also provide a non-iframe way to identify and
   open the location.
4. See Finding 1: present behavior is verified, but the keyless endpoint has no current official
   embed documentation from which a stability or deprecation guarantee can be inferred.
